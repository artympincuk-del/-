# Telegram AI Assistant Bot

AI-ассистент для Telegram на aiogram 3, использующий Groq (бесплатный API,
модели OpenAI GPT-OSS 20B/120B, плюс Qwen для фото). Дневной бесплатный
лимит сообщений, докупка пакетов/безлимита/месячной подписки за Telegram
Stars, реферальная программа, опциональные напоминания и админ-панель со
статистикой/воронкой продаж.

## Что уже сделано (кратко, по блокам)

Ориентир для быстрого входа в проект — не история коммитов, а что именно
работает и почему так:

1. **Платежи.** `drop_pending_updates=False`, чтобы `successful_payment` не
   терялся при передеплое. Начисление атомарно и идемпотентно по
   `telegram_payment_charge_id` (повторная доставка апдейта не начисляет
   дважды). Pre-checkout сверяет пакет/цену с текущими `PACKAGES` через
   `PRICE_VERSION` — старый счёт после смены цен отклоняется, а не
   недо-/пере-начисляет. `/refund` — реальный возврат через Stars API.
2. **История диалога.** Перенесена из `aiogram` `MemoryStorage` (терялась
   при каждом рестарте) в SQLite (`dialog_history`), с тем же капом по
   ходам (`MAX_HISTORY_TURNS`), но персистентно. `/reset` чистит её в БД.
3. **Защита рефералки от накрутки.** Бонус пригласившему — не сразу, а
   после того как приглашённый пришлёт `REFERRAL_MIN_MESSAGES` реальных
   сообщений, плюс дневной кап на число оплаченных приглашений с одного
   аккаунта. Приглашённый получает свою часть сразу (это не эксплуатируемо
   фейковыми аккаунтами) — см. «Реферальная программа» ниже.
4. **Общая надёжность.** Per-user `asyncio.Lock` + глобальный
   `asyncio.Semaphore` на Groq (один пользователь не может залить общий
   rate limit параллельными сообщениями), SQLite в режиме WAL, дневной
   лимит и отображаемое время — в таймзоне `QUOTA_TZ`, а не в сыром UTC,
   проверка моделей у Groq при старте, корректное закрытие сессии/БД при
   остановке. Подробности — «Надёжность» ниже.
5. **Хранение переписки.** `chat_log` (админский аудит для разбора
   обращений) больше не растёт бесконечно — ретеншен `CHATLOG_RETENTION_DAYS`
   с фоновой чисткой; `/start` и `/help` честно предупреждают, что
   переписка сохраняется.
6. **Монетизация.** Месячная подписка за Stars с автопродлением и отменой
   (`createInvoiceLink` + `editUserStarSubscription`), воронка продаж
   (таблица `events`, экран конверсии в `/admin`), опциональные
   ежедневные напоминания (строго по явному согласию пользователя).

## Архитектура (для ИИ/разработчика — читай это вместо всего кода)

Живой бот: `@Paknym_bot` на Railway (сервис `telegram-roulette-bot`, ветка
`claude/telegram-bot-roulette-vhdyts`, автодеплой не настроен — нужен явный
`railway service source connect ... && railway up`/пересборка после пуша).

Файлы:
- **`bot/main.py`** — точка входа: создаёт `Bot`/`Dispatcher` (parse_mode по
  умолчанию HTML), регистрирует команды меню, при старте проверяет
  доступность моделей из конфига через Groq (`ai.check_configured_models()`,
  пишет warning в лог, если модели нет), запускает polling; при остановке
  закрывает HTTP-сессию бота и соединение с БД (`db.close()`).
- **`bot/handlers.py`** — весь Telegram-слой (самый большой файл, >1000
  строк): все `@router` хендлеры — инлайн-меню, баланс/покупки, заметки,
  фото/PDF/voice, реферальная система, групповые чаты, админ-панель
  (`/admin`). Ключевые паттерны:
  - `MODEL_OPTIONS[(tier, choice)]` — `tier` = `fast`/`premium` (тариф
    биллинга/квоты), `choice` = `gptoss`/`llama` (какой именно движок
    Groq); `_model_option(status)` резолвит текущий выбор пользователя.
  - `_edit_or_send()` — все инлайн-меню редактируют сообщение на месте
    (не спамят новыми), `parse_mode=None` передаётся явно для экранов с
    сырым пользовательским текстом (чатлог), чтобы `<`/`&` не ломали HTML.
  - Фото идёт в два прохода: `VISION_MODEL` (Qwen) только описывает
    содержимое, затем `PREMIUM_MODEL` с `reasoning_effort="high"` решает —
    это всегда сильнейшая модель, независимо от выбора пользователя в
    `/model` (для точности).
- **`bot/ai.py`** — вся логика Groq API: `ask_ai()` (с ретраем на меньший
  `reasoning_effort` при обрезании ответа), `generate_image()` (Pollinations,
  анонимно, бесплатно и без лимита — модель `flux` + перевод промпта на
  английский), `edit_image()` (Pollinations, модель `kontext` — редактирует
  реальное фото, требует `POLLINATIONS_API_KEY`, см. «Редактирование фото»
  ниже), `transcribe_audio()` (Whisper), поиск в интернете как tool-calling
  (`search_web`, DuckDuckGo с фолбэком бэкендов).
- **`bot/db.py`** — SQLite (`players`, `notes`, `chat_log`, `payments`,
  `dialog_history`, `referrals`, `events`). Важно: `get_status()`/`try_consume_message()`
  **упсертят** игрока и обновляют `last_active_at` — для read-only
  админ-обращений использовать `get_player()` (не трогает
  активность/username). `admin_add_bonus_credits()` — для начислений от
  админа (не создаёт фантомных строк, не бьёт статистику активности).
  `record_payment_and_credit()` — единственный правильный способ зачислить
  оплату: атомарно (одна транзакция) и идемпотентно по
  `telegram_payment_charge_id` (уникальный индекс) — повторная доставка
  апдейта не начислит дважды. `refund_payment()` — обратная операция.
  `get_dialog_history()`/`append_dialog_turn()`/`clear_dialog_history()` —
  контекст диалога, отдаваемый модели на каждом ходу (не путать с
  `chat_log` — это админский аудит-лог всей переписки, никогда не
  подрезается и не читается обратно в промпт). `register_referral()` +
  `try_credit_referral_message()` — реферальный бонус начисляется отложенно
  и capped, см. «Реферальная программа» ниже; при начислении оба игрока
  апсертятся напрямую (без `_ensure_player()`), чтобы не бить
  `last_active_at` за чужое действие.
- **`bot/config.py`** — все переменные окружения одним местом (модели,
  лимиты, `ADMIN_IDS`, `DB_PATH`).
- **`bot/payments.py`** — пакеты Stars (`PACKAGES` — сообщения,
  `TIME_PACKAGES` — безлимит по времени, `SUBSCRIPTION` — месячная подписка),
  их клавиатура и `PRICE_VERSION` + `resolve_package()`: версия зашивается в
  payload инвойса, чтобы старый счёт (открытый до смены цен) отклонялся на
  pre-checkout, а не списывал неверную сумму. `PRICE_VERSION` — константа в
  этом файле, не в `config.py`/`.env`: она обязана меняться вместе с
  `PACKAGES` в одном коммите, а не как отдельная env-переменная, которая
  может рассинхронизироваться (`SUBSCRIPTION_PRICE_STARS` — единственное
  исключение, живёт в `config.py`, см. «Монетизация» ниже).

Хранилище — SQLite на Railway Volume (см. «Деплой на Railway» ниже); без
Volume база сбрасывается при каждом деплое.

## Меню и команды

Главное меню — инлайн-кнопки (открывается по `/start` или `/menu`):
Баланс, Пополнить, Модель, Заметки, Сбросить диалог, Помощь.

- `/start`, `/menu` — открыть меню
- `/model` — выбрать модель: быстрая (GPT-OSS 20B, с бесплатным лимитом)
  или премиум (GPT-OSS 120B с глубоким рассуждением, бесплатный лимит +
  докупленные сообщения)
- `/balance` — остаток дневного лимита и докупленных сообщений
- `/buy` — купить пакет сообщений за Telegram Stars
- `/remember <текст>` / «Запомни: ...» — сохранить заметку о себе, которую
  бот учитывает в каждом ответе; `/notes` — список, `/forget <номер>` — удалить
- `/image <описание>` / «нарисуй ...» — сгенерировать картинку (Pollinations,
  модель `flux`, анонимно и бесплатно). Из того же экрана («Картинка» в
  меню) можно вместо текста прислать фото с подписью — это отредактирует
  именно это фото (`kontext`, см. «Редактирование фото» ниже), а не
  нарисует новое. Оба варианта биллятся `db.try_consume_image()` — свой
  отдельный дневной лимит `DAILY_FREE_IMAGE_MESSAGES`, **не общий** с
  премиум-чатом (генерация с нуля бесплатна для нас, а вот редактирование
  стоит реальных денег за вызов, поэтому у картинок свой независимый
  дневной потолок, который можно крутить не трогая лимит обычных
  премиум-ответов), а когда лимит кончился — `PREMIUM_CREDIT_COST`
  докупленных сообщений за картинку (раньше был отдельный флэт
  `IMAGE_CREDIT_COST` из `bonus_credits`, потом недолго делили с премиум-
  чатом через `force_premium=True` — оба подхода заменены на отдельный
  пул)
- `/invite` — реферальная ссылка: бонус начисляется не сразу, а после того
  как приглашённый напишет боту (см. «Реферальная программа» ниже)
- `/promo <код> <слово>` — привязать себя как партнёра к промокоду от
  админа (слово выдаёт админ, без него не привязать); `/mypromo` — своя
  статистика по коду (см. «Промокоды партнёров» ниже)
- `/reset` — сбросить историю диалога (хранится в БД, `/reset` физически
  удаляет её для этого пользователя)
- `/whoami` — узнать свой Telegram ID
- `/help` — подробности

История диалога (контекст, который видит модель) хранится в SQLite
(`dialog_history`), а не в оперативной памяти — переживает рестарт/деплой,
как и баланс. Обрезается до последних `MAX_HISTORY_TURNS` ходов
(`bot/config.py`, по умолчанию 10) — как при чтении контекста для модели,
так и физически в таблице, чтобы она не росла бесконечно.

Обычное текстовое сообщение и голосовые (распознаются через Groq Whisper)
уходят текстовой модели с доступом к поиску в интернете (DuckDuckGo,
tool-calling — модель сама решает, когда искать свежую информацию). Фото
разбираются в два этапа (сначала точное распознавание, потом решение
премиум-моделью) — можно с подписью-вопросом. PDF-файлы читаются через pypdf
и передаются модели как контекст. Под каждым текстовым ответом — кнопки
«Подробнее» / «Проще» / «Пример» для быстрого уточнения без повторного ввода
вопроса. Есть пакет безлимита по времени (1 час) — не считает отдельные
сообщения, пока активен.

### Групповые чаты

Бот отвечает в группах, только если его упомянуть (`@имя_бота`) или ответить
на его сообщение — иначе он не реагирует на каждое сообщение в чате. Это
работает «из коробки» при стандартной настройке @BotFather — **Group
Privacy** должен оставаться **включённым** (значение по умолчанию): тогда
Telegram сам доставляет боту в группах только упоминания/ответы/команды, а
код бота дополнительно на всякий случай проверяет то же самое. Отключать
privacy mode не нужно — с ним бот получал бы вообще все сообщения в группе.

### Админ-панель

Telegram ID из `ADMIN_IDS` (через запятую) получают доступ к `/admin` —
инлайн-панели со статистикой (пользователи, активность, доход в звёздах за
день/7 дней/всего) и постраничным списком пользователей; по каждому
пользователю — карточка с балансом, последними платежами (с charge_id и
статусом paid/refunded) и кнопками начисления (+10/+50/-10), чатлога и
возврата оплаты, без необходимости печатать ID вручную. Старые текстовые
команды тоже работают:
- `/grant <@username или id> <amount>` — начислить/списать сообщения
- `/users` — список пользователей и их лимитов
- `/chatlog <@username или id> [N]` — последние N сообщений переписки
- `/refund <telegram_payment_charge_id>` — вернуть оплату через Stars API
  (`bot.refund_star_payment`) и списать выданное обратно (баланс сообщений
  не уходит в минус); работает только для платежей после этой миграции —
  у них есть сохранённый `telegram_payment_charge_id`, у более старых его нет
- `/promo_add <код> <название> <бонус_минут> <доля_%> <окно_дней>` — создать
  промокод (в ответ придёт секретное слово для партнёра и готовый текст
  ссылки — сохрани, больше слово нигде не покажется); `/promo_off <код>` —
  выключить (не трогает уже привязанных); `/promo_list` — все коды с
  ключевыми цифрами; `/promo_stat <код>` — статистика по одному коду;
  `/promo_owner <код> <@username или id>` — принудительно назначить
  владельца без проверки слова (`0` вместо id — снять владельца);
  `/promo_token <код>` — посмотреть слово, `/promo_token <код> new` —
  перегенерировать, если слово утекло (см. «Промокоды партнёров» ниже)
- Все админские команды с указанием пользователя понимают `@username`,
  `@USERNAME` и голый `username` без `@` одинаково (регистр не важен,
  ищут по последнему известному username — он обновляется при каждом
  сообщении от человека боту) — а также числовой Telegram id, если
  username неизвестен. `_resolve_target()` в `handlers.py`, общая для всех.

### Платежи (Telegram Stars)

- Оплата не теряется при передеплое: бот запускается с
  `drop_pending_updates=False`, так что накопившиеся во время рестарта
  апдейты (включая `successful_payment`) не отбрасываются, а обрабатываются
  при следующем старте.
- Начисление идемпотентно: каждый платёж сохраняется с уникальным
  `telegram_payment_charge_id` — если Telegram повторно доставит тот же
  `successful_payment` (например, из-за рестарта в процессе доставки),
  повторного начисления не будет, пользователь получит сообщение «платёж уже
  обработан».
- На pre-checkout бот проверяет, что оплачиваемый пакет реально существует
  в текущих `PACKAGES`/`TIME_PACKAGES`/`SUBSCRIPTION` и цена совпадает —
  иначе отклоняет платёж с понятной причиной, а не берёт деньги за
  несуществующий/устаревший пакет.
- Таблица `payments`: `kind` (`messages`/`unlimited`/`subscription`),
  `amount_stars`, `credited_amount` (сколько сообщений/минут/дней реально
  выдано — не зависит от последующих изменений цен), `telegram_payment_charge_id`,
  `status` (`paid`/`refunded`).

### Монетизация

**Подписка за Stars** (месячная, автопродление): в отличие от разовых
пакетов, создаётся через `bot.create_invoice_link(..., subscription_period=2592000)`
— у `send_invoice`/`answer_invoice` параметра подписки нет вообще, только у
`createInvoiceLink` (Telegram сейчас разрешает только ровно 30 дней).
Ссылка отдаётся пользователю кнопкой `url=...`, а не открывается как обычный
инвойс. Каждое продление приходит отдельным `successful_payment` с новым
`telegram_payment_charge_id`, но тем же `invoice_payload` — идемпотентность
из блока платежей (уникальный индекс по charge_id) сама отличает
редоставленный дубль (не начисляет повторно) от настоящего продления
(стакает ещё 30 дней). Состояние — прямо в `players`:
`subscription_until` (до какой даты активна, стакается как безлимит-пассы),
`subscription_status` (`none`/`active`/`canceled`), `subscription_charge_id`
(последний charge_id — нужен, чтобы вызвать `editUserStarSubscription` для
отмены). Отмена/возобновление — кнопка в «Баланс», которая сначала дёргает
Telegram (`bot.edit_user_star_subscription`) и только при успехе меняет
статус локально; отмена не обрывает доступ сразу, только останавливает
автопродление. `SUBSCRIPTION_PRICE_STARS` — в `config.py` (единственная
цена, вынесенная из `payments.py`, так и было явно запрошено); при смене
всё равно нужно бампнуть `PRICE_VERSION` в `payments.py` в том же деплое.

Подписка **не безлимитна** — честный дневной лимит (`SUBSCRIPTION_DAILY_MESSAGES`/
`SUBSCRIPTION_DAILY_PREMIUM_MESSAGES` в `config.py`, по умолчанию 30/15),
больше бесплатного, но не бесконечный: один тяжёлый подписчик на плоской
месячной цене не должен съедать всю маржу. Списывается через те же счётчики
`messages_used_today`/`premium_messages_used_today`, что и бесплатный тариф
(`db.try_consume_message`), просто сравнивается с другим лимитом — поэтому
`refund_consumed_message` работает без изменений что для бесплатного
пользователя, что для подписчика. Когда дневной лимит подписки исчерпан,
доступ не блокируется — списывается `bonus_credits`, как и у всех; если и
их нет — отказ с понятным текстом («лимит обновится в 00:00 по МСК»,
без предложения «оформи подписку», раз она уже есть). Активный безлимит-пасс
(`TIME_PACKAGES`) по-прежнему приоритетнее и обходит эти лимиты целиком.

**Воронка покупок**: таблица `events` (`user_id`, `event`, `created_at`) —
логируются `buy_opened` (открыт экран покупки — и «Баланс», и «Пополнить»),
`invoice_sent` (создан инвойс/ссылка) и `paid` (успешно оплачено, не
дубликат). `/admin` → «📈 Воронка покупок» — конверсия по уникальным
пользователям, отдельно за сегодня и за 7 дней, с процентами между этапами.

**Опциональные напоминания**: кнопка «🔔 Напоминания» в меню — по умолчанию
выключены, включаются и выбираются только самим пользователем (пресеты
09:00–21:00 по `QUOTA_TZ`). Фоновая задача в `main.py`
(`_reminder_loop`, проверка каждые 5 минут) шлёт `players.reminder_hour`
ровно раз в сутки (`reminder_last_sent_date` защищает от повтора) —
никаких рассылок без явного включения, отключить можно в любой момент.

### Реферальная программа

Асимметрично по таймингу — защита от накрутки фейковыми аккаунтами:
- Приглашённый получает `REFERRAL_SIGNUP_BONUS` (по умолчанию 5 сообщений)
  сразу при переходе по ссылке — не гейтится, фейковому аккаунту с парой
  бесплатных сообщений на собственном одноразовом балансе ничего не даёт.
- Пригласившему `REFERRAL_BONUS_MESSAGES` (по умолчанию 20 сообщений)
  начисляется отложенно — только когда приглашённый напишет боту
  `REFERRAL_MIN_MESSAGES` (по умолчанию 3) реальных сообщений (текст, фото
  или PDF — генерация картинок не считается). Плюс дневной лимит
`REFERRAL_DAILY_CAP` (по умолчанию 5) на число *оплаченных* приглашений от
одного пригласившего в сутки — даже если завести сколько угодно фейковых
аккаунтов и разогнать их до порога сообщений, реально обналичить
получится не больше `REFERRAL_DAILY_CAP` в день. Приглашения, упёршиеся в
дневной лимит, не сгорают — остаются `pending` и оплачиваются сами, как
только у пригласившего освобождается место в лимите (на следующий день
или раньше).

Таблица `referrals`: одна строка на приглашённого (`user_id` — PK),
`referrer_id`, `status` (`pending`/`paid`), `message_count`, `paid_at`.
Отдельно от `players.referred_by`, который остаётся как есть (только для
идемпотентности «пригласили один раз, не сам себя»).

### Промокоды партнёров (блогеров)

Полностью независимо от реферальной программы выше — своя пара таблиц,
свой deep-link-префикс, ничего общего в данных. Механика: админ создаёт
нейтральный код (`tt1`, `yt1` — без имени партнёра, оно только в `title`
для админки) через `/promo_add`, партнёр привязывает себя к коду через
`/promo <код> <слово>`, делится ссылкой `t.me/<bot>?start=promo_<код>`.

- **Привязка владельца — по секретному слову, не «кто первый».** Код сам
  публичный (виден в ссылке), поэтому одного кода недостаточно: у каждого
  кода есть `claim_token` (8 символов, `secrets.choice`, без похожих
  символов `0 O o 1 l I`) — `/promo <код> <слово>` требует оба. Неверный
  код и неверное слово отвечают одинаковым нейтральным текстом, чтобы по
  ответу нельзя было понять, существует ли код вообще. Уже занятый код не
  отдаётся другому даже с верным словом — для принудительной замены есть
  админская `/promo_owner <код> <@username или id>` (без проверки слова;
  `/promo_owner <код> 0` снимает владельца). Слово можно посмотреть
  (`/promo_token <код>`) или перегенерировать (`/promo_token <код> new`,
  старое сразу перестаёт работать) — нигде, кроме этих команд и
  подтверждения `/promo_add`, слово не показывается (в `/promo_list`,
  например, его нет).
- Переход по ссылке (`cmd_start` → `_apply_promo`, параллельно
  `_apply_referral`) выдаёт бонус через `db.activate_promo_bonus` —
  отдельная колонка `players.promo_bonus_until`, **не** `unlimited_until`
  (это поле зарезервировано за настоящим купленным почасовым безлимитом,
  его логика вообще не тронута). Только один раз на пользователя:
  `promo_visits.user_id` — PK, «первый код победил», как и
  `players.referred_by`. Владелец кода не может активировать свою же
  ссылку. Неизвестный/выключенный код — молча обычное приветствие, без
  сообщений об ошибке.
- **Бонус не безлимитный — свой дневной потолок.** Публичная ссылка на
  бесплатные Telegram-аккаунты без потолка была бы неограниченным краном
  API-расходов. `try_consume_message` считает бонус по тем же счётчикам
  `messages_used_today`/`premium_messages_used_today`, что и подписка/free,
  просто сравнивает с `PROMO_BONUS_DAILY_MESSAGES`/
  `PROMO_BONUS_DAILY_PREMIUM_MESSAGES` (`config.py`). Порядок проверки:
  купленный безлимит → промо-бонус → подписка → free + `bonus_credits`
  (промо-бонус раньше подписки, потому что он сгорает по дате, а подписка
  нет).
- **Складывание с подпиской — не всегда.** В момент выдачи бонуса
  (`activate_promo_bonus`) фиксируется `players.promo_bonus_stacks`: `1`,
  если подписки ещё не было (лимиты бонуса и подписки потом суммируются,
  если человек оформит её внутри окна бонуса — поощрение за конверсию),
  `0`, если подписка уже была (лимиты не складываются, берётся больший из
  двух — иначе действующий подписчик удваивал бы себе лимит одним кликом
  по публичной ссылке). Чистая функция `db.promo_effective_limits(...)`
  считает эту арифметику один раз и переиспользуется и при списании
  (`try_consume_message`), и при отображении (`_balance_text`,
  `quota_denied_text`), чтобы цифры нигде не разъехались. Флаг имеет
  значение только пока активно `promo_bonus_until` — после истечения
  бонуса человек просто падает на подписку/free как обычно.
- В «Балансе» подписка и бонус — две отдельные строки (подписка не
  пропадает с экрана только из-за активного бонуса), а дневной лимит,
  если он сложился, показывается одним итоговым числом, не двумя.
- Код **не отключается сам** ни по времени, ни по числу переходов —
  только вручную, `/promo_off`. Отключение не трогает уже привязанных
  пользователей: их оплаты продолжают засчитываться партнёру, пока не
  истечёт их персональное окно атрибуции.
- Атрибуция оплат: колонка `payments.promo_code`, проставляется в
  `record_payment_and_credit()` на основе `promo_visits` — партнёру
  засчитывается оплата, только если с момента *его собственного* перехода
  (`joined_at`) прошло меньше `window_days` дней. Окно — per-user, не
  привязано ни к дате создания кода, ни к моменту его отключения.
- Партнёрская доля — `revenue_stars * revenue_share // 100` (округление
  вниз), считается на лету в `db.get_promo_stats()`/`list_promo_codes()`,
  нигде не хранится отдельно.
- `/mypromo` — статистика партнёру по его коду (переходы, «пользовались
  ботом хоть раз» — есть строка в `chat_log` с `role='user'`, просто
  `/start` не считается, — оплаты, доля, сколько сейчас внутри окна
  атрибуции). Доступ у любого, кто привязан как `owner_user_id`; чужой
  код чужому не покажет ничего, потому что `get_promo_code_by_owner`
  ищет строго по своему `user_id`. `/promo_list`/`/promo_stat <код>` —
  то же самое для админов, плюс `title` и `owner_user_id`, которые
  партнёру не показываются (но не слово — оно нигде в статистике не
  участвует).

### Редактирование фото

Отдельно от генерации с нуля (`generate_image`/`flux`, бесплатно и
анонимно). Реальное редактирование присланного фото — `ai.edit_image()`,
модель `kontext`, через `POST gen.pollinations.ai/v1/images/edits`.

- **Байты, а не ссылка — сознательный выбор.** У `kontext` есть и бесплатный
  анонимный GET-режим (`image.pollinations.ai/prompt/...?model=kontext&
  image=<URL>`), но он принимает только ссылку на фото, а единственная
  ссылка, которая есть у бота — Telegram-ссылка на файл вида
  `api.telegram.org/file/bot<TOKEN>/...`, с `BOT_TOKEN` прямо в URL.
  Отправить такую ссылку стороннему сервису значит слить токен бота
  полностью — кто угодно с доступом к их логам получил бы контроль над
  ботом. Поэтому `edit_image()` вместо этого качает фото самостоятельно
  (`message.bot.download`) и шлёт multipart POST с самими байтами —
  ссылка на Telegram никуда не уходит.
- Платный (не входит в бесплатный анонимный тир Pollinations, в отличие от
  `flux`) — нужен `POLLINATIONS_API_KEY` (https://enter.pollinations.ai/keys,
  ~$0.04/правка). Без ключа `edit_image()` не падает — `AIError` с понятным
  «Редактирование фото сейчас недоступно», генерация с нуля продолжает
  работать как обычно.
- **Точка входа** — тот же экран «🎨 Генерация картинок» (`/image`, кнопка
  «Картинка»): вместо текста туда можно прислать фото с подписью
  (`Form.waiting_for_image_prompt` теперь ловит и `F.photo`, не только
  `F.text`). Обычная отправка фото боту (без захода в этот экран) по-прежнему
  идёт в пайплайн решения задач (`_handle_photo_message_locked`) — эти два
  пути не пересекаются, разграничены исключительно FSM-состоянием.
- **«Ещё раз»/«Изменить»** под результатом работают и для редактирования, не
  только для генерации — `last_image_mode` («generate»/«edit») в FSM
  различает, что переиспользовать: текстовый промпт (перегенерировать через
  `flux`) или `last_image_file_id` (применить новую правку через `kontext`
  поверх последнего результата — то есть правки чейнятся одна на другую, а
  не всегда возвращаются к самому первому загруженному фото).
- Биллинг идентичен генерации — общий `DAILY_FREE_IMAGE_MESSAGES` (см. ниже),
  тот же рефанд при ошибке.

### Дневной лимит на картинки — отдельный от премиум-чата

`db.try_consume_image()` — своя пара (`images_used_today` в `players`,
`DAILY_FREE_IMAGE_MESSAGES` в `config.py`), не пересекается ни с
`messages_used_today`/`premium_messages_used_today`, ни с их лимитами.
Причина в том, что реальные деньги тратятся только на редактирование
(`kontext`, ~$0.04 за вызов) — генерация с нуля (`flux`) бесплатна всегда,
но раз генерация и редактирование неотличимы для пользователя на старте
(оба через экран «Картинка»), лимит у них общий. Так `DAILY_FREE_IMAGE_MESSAGES`
можно крутить независимо от `DAILY_FREE_PREMIUM_MESSAGES` — это единственный
рычаг, который напрямую управляет реальным расходом на API. Флэт: подписка
и промо-бонус НЕ дают повышенного лимита на картинки (в отличие от
премиум-чата) — сознательное упрощение первой версии; активный купленный
почасовой безлимит по-прежнему освобождает от лимита полностью, как и
везде. Fallback после исчерпания — `bonus_credits` по `PREMIUM_CREDIT_COST`,
тот же паттерн, что и у обычных премиум-сообщений. `/balance` показывает
использование отдельной строкой «Картинки сегодня: X/Y».

### Надёжность

- **Параллельный спам одного пользователя**: per-user `asyncio.Lock`
  (`handlers._get_user_lock`) — пока обрабатывается предыдущее сообщение
  этого пользователя, новое не запускается, в ответ приходит «⏳ Дождись
  ответа на предыдущее сообщение». Не влияет на других пользователей —
  лимит запросов от разных людей друг друга не блокирует.
- **Общий лимит на Groq**: глобальный `asyncio.Semaphore(GROQ_MAX_CONCURRENT)`
  в `bot/ai.py` оборачивает все три места, где код реально стучится в Groq
  (chat completions, STT, перевод промпта для картинки) — не даёт всем
  пользователям вместе выжечь общий rate limit одновременными запросами.
- **SQLite**: при подключении выставляются `PRAGMA journal_mode=WAL`,
  `busy_timeout=5000`, `synchronous=NORMAL` — читатели не блокируют писателя,
  а конкурентная запись ждёт до 5 сек вместо мгновенного "database is locked".
- **Часовой пояс**: дневной лимит сообщений и дневной кап рефералов считают
  сутки по `QUOTA_TZ` (IANA-имя, по умолчанию `Europe/Moscow`) через
  `zoneinfo`, а не по UTC — раньше сброс лимита приходился на 3 часа ночи
  по Москве. Время окончания безлимита показывается пользователю тоже в
  `QUOTA_TZ`, а не в сыром UTC. Все таймстампы в БД по-прежнему хранятся как
  наивные UTC-строки (см. `db._utcnow_naive()`/`db._today_start_utc()`) —
  меняется только то, в каком поясе считаются календарные сутки и что
  показывается пользователю, формат хранения не тронут (иначе сравнения со
  старыми записями сломались бы).
- **Проверка моделей при старте**: `ai.check_configured_models()` запрашивает
  у Groq список доступных моделей и пишет warning в лог для каждой
  настроенной модели (`FAST_MODEL`/`PREMIUM_MODEL`/`VISION_MODEL`/`STT_MODEL`),
  которой там нет — вместо того, чтобы опечатка в id модели вылезала только
  в рантайме на первом же фото/голосовом.
- **Корректное завершение**: при остановке бот закрывает HTTP-сессию
  (`bot.session.close()`) и соединение с БД (`db.close()`, коммитит и
  закрывает) вместо того, чтобы полагаться на обрыв процесса.
- **Ретеншен переписки**: `chat_log` (админский аудит-лог, см. `/chatlog`
  выше — доступ к нему не убран) хранится `CHATLOG_RETENTION_DAYS` дней (по
  умолчанию 30), старые записи удаляются при старте и затем раз в сутки
  фоновой задачей (`main._chatlog_retention_loop`) — иначе таблица растёт
  на диске Railway бесконечно. `dialog_history` в этот ретеншен не входит,
  у неё свой отдельный кап по `MAX_HISTORY_TURNS` (см. выше).
- **Глобальный обработчик ошибок**: `main.on_error` (`dp.errors.register(...)`,
  `aiogram` `ErrorEvent`) — без него любое исключение, не пойманное в
  хендлере, просто уходило в лог, а пользователь не получал вообще ничего.
  Логирует полный трейсбек с `user_id`/типом апдейта и шлёт короткое «Что-то
  пошло не так...». Сам обёрнут так, что не может упасть; `ai.AIError` сюда
  никогда не долетает — все точки вызова Groq уже перехватывают её локально
  и показывают своё понятное сообщение.
- **Запрос не тратится впустую при ошибке**: `try_consume_message()` теперь
  возвращает `status["consumed"]` (какой именно бакет списан — дневная
  квота/премиум-квота/докупленные сообщения — и сколько), а
  `db.refund_consumed_message()` откатывает это обратно. Во всех трёх
  пайплайнах (текст, PDF, фото) — и на `ai.AIError`, и на любое другое
  исключение после списания квоты (с `raise` дальше, чтобы сработал
  глобальный обработчик выше) — списанное возвращается пользователю. Не
  списывается вообще, если доступ был по безлимиту/подписке
  (`status["consumed"] is None`).

## Локальный запуск

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env  # впиши свои BOT_TOKEN и GROQ_API_KEY
python -m bot.main
```

Ключ Groq берётся на https://console.groq.com/keys (бесплатно, без карты).

## Деплой на Railway

Перед каждым пушем — быстрая статическая проверка (ловит необъявленные
имена, опечатки в переменных и прочие вещи, которые иначе всплывают только
в рантайме на конкретном пользователе):

```bash
pip install -r requirements-dev.txt
python -m pyflakes bot/*.py
```

Пустой вывод — значит всё чисто. Только после этого — деплой:

1. Зайди на https://railway.app и залогинься через GitHub.
2. **New Project → Deploy from GitHub repo** → выбери этот репозиторий и ветку.
3. В настройках проекта (Variables) добавь:
   - `BOT_TOKEN` — токен бота от @BotFather
   - `GROQ_API_KEY` — ключ от console.groq.com
4. Railway автоматически соберёт проект (Nixpacks) и запустит команду из
   `railway.json` / `Procfile` (`python -m bot.main`).

Баланс/лимиты/заметки хранятся в SQLite-файле. На бесплатном плане Railway
диск по умолчанию эфемерный и сбрасывается при каждом деплое — обязательно
подключи Railway Volume (`railway volume add --mount-path /data`) и укажи
путь через него в переменной `DB_PATH` (например `/data/assistant.db`),
иначе все балансы и покупки будут пропадать при каждом обновлении кода.
