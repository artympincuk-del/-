# Telegram AI Assistant Bot

AI-ассистент для Telegram на aiogram 3, использующий Groq (бесплатный API,
модели OpenAI GPT-OSS 20B/120B, плюс Qwen для фото). Есть дневной бесплатный
лимит сообщений и докупка дополнительных сообщений за Telegram Stars.

## Архитектура (для ИИ/разработчика — читай это вместо всего кода)

Живой бот: `@Paknym_bot` на Railway (сервис `telegram-roulette-bot`, ветка
`claude/telegram-bot-roulette-vhdyts`, автодеплой не настроен — нужен явный
`railway service source connect ... && railway up`/пересборка после пуша).

Файлы:
- **`bot/main.py`** — точка входа: создаёт `Bot`/`Dispatcher` (parse_mode по
  умолчанию HTML), регистрирует команды меню, при старте проверяет
  доступность моделей из конфига через Groq (`ai.check_configured_models()`,
  пишет warning в лог, если модели нет), запускает polling; при остановке
  закрывает HTTP-сессию бота и соединение с БД (`db.close()`).
- **`bot/handlers.py`** — весь Telegram-слой (самый большой файл, >1000
  строк): все `@router` хендлеры — инлайн-меню, баланс/покупки, заметки,
  фото/PDF/voice, реферальная система, групповые чаты, админ-панель
  (`/admin`). Ключевые паттерны:
  - `MODEL_OPTIONS[(tier, choice)]` — `tier` = `fast`/`premium` (тариф
    биллинга/квоты), `choice` = `gptoss`/`llama` (какой именно движок
    Groq); `_model_option(status)` резолвит текущий выбор пользователя.
  - `_edit_or_send()` — все инлайн-меню редактируют сообщение на месте
    (не спамят новыми), `parse_mode=None` передаётся явно для экранов с
    сырым пользовательским текстом (чатлог), чтобы `<`/`&` не ломали HTML.
  - Фото идёт в два прохода: `VISION_MODEL` (Qwen) только описывает
    содержимое, затем `PREMIUM_MODEL` с `reasoning_effort="high"` решает —
    это всегда сильнейшая модель, независимо от выбора пользователя в
    `/model` (для точности).
- **`bot/ai.py`** — вся логика Groq API: `ask_ai()` (с ретраем на меньший
  `reasoning_effort` при обрезании ответа), `generate_image()` (Pollinations
  + перевод промпта на английский), `transcribe_audio()` (Whisper), поиск в
  интернете как tool-calling (`search_web`, DuckDuckGo с фолбэком бэкендов).
- **`bot/db.py`** — SQLite (`players`, `notes`, `chat_log`, `payments`,
  `dialog_history`, `referrals`, `events`). Важно: `get_status()`/`try_consume_message()`
  **упсертят** игрока и обновляют `last_active_at` — для read-only
  админ-обращений использовать `get_player()` (не трогает
  активность/username). `admin_add_bonus_credits()` — для начислений от
  админа (не создаёт фантомных строк, не бьёт статистику активности).
  `record_payment_and_credit()` — единственный правильный способ зачислить
  оплату: атомарно (одна транзакция) и идемпотентно по
  `telegram_payment_charge_id` (уникальный индекс) — повторная доставка
  апдейта не начислит дважды. `refund_payment()` — обратная операция.
  `get_dialog_history()`/`append_dialog_turn()`/`clear_dialog_history()` —
  контекст диалога, отдаваемый модели на каждом ходу (не путать с
  `chat_log` — это админский аудит-лог всей переписки, никогда не
  подрезается и не читается обратно в промпт). `register_referral()` +
  `try_credit_referral_message()` — реферальный бонус начисляется отложенно
  и capped, см. «Реферальная программа» ниже; при начислении оба игрока
  апсертятся напрямую (без `_ensure_player()`), чтобы не бить
  `last_active_at` за чужое действие.
- **`bot/config.py`** — все переменные окружения одним местом (модели,
  лимиты, `ADMIN_IDS`, `DB_PATH`).
- **`bot/payments.py`** — пакеты Stars (`PACKAGES` — сообщения,
  `TIME_PACKAGES` — безлимит по времени, `SUBSCRIPTION` — месячная подписка),
  их клавиатура и `PRICE_VERSION` + `resolve_package()`: версия зашивается в
  payload инвойса, чтобы старый счёт (открытый до смены цен) отклонялся на
  pre-checkout, а не списывал неверную сумму. `PRICE_VERSION` — константа в
  этом файле, не в `config.py`/`.env`: она обязана меняться вместе с
  `PACKAGES` в одном коммите, а не как отдельная env-переменная, которая
  может рассинхронизироваться (`SUBSCRIPTION_PRICE_STARS` — единственное
  исключение, живёт в `config.py`, см. «Монетизация» ниже).

Хранилище — SQLite на Railway Volume (см. «Деплой на Railway» ниже); без
Volume база сбрасывается при каждом деплое.

## Меню и команды

Главное меню — инлайн-кнопки (открывается по `/start` или `/menu`):
Баланс, Пополнить, Модель, Заметки, Сбросить диалог, Помощь.

- `/start`, `/menu` — открыть меню
- `/model` — выбрать модель: быстрая (GPT-OSS 20B, с бесплатным лимитом)
  или премиум (GPT-OSS 120B с глубоким рассуждением, бесплатный лимит +
  докупленные сообщения)
- `/balance` — остаток дневного лимита и докупленных сообщений
- `/buy` — купить пакет сообщений за Telegram Stars
- `/remember <текст>` / «Запомни: ...» — сохранить заметку о себе, которую
  бот учитывает в каждом ответе; `/notes` — список, `/forget <номер>` — удалить
- `/image <описание>` / «нарисуй ...» — сгенерировать картинку (Pollinations,
  платно — списывает докупленные сообщения, отдельно от обычного лимита)
- `/invite` — реферальная ссылка: бонус начисляется не сразу, а после того
  как приглашённый напишет боту (см. «Реферальная программа» ниже)
- `/reset` — сбросить историю диалога (хранится в БД, `/reset` физически
  удаляет её для этого пользователя)
- `/whoami` — узнать свой Telegram ID
- `/help` — подробности

История диалога (контекст, который видит модель) хранится в SQLite
(`dialog_history`), а не в оперативной памяти — переживает рестарт/деплой,
как и баланс. Обрезается до последних `MAX_HISTORY_TURNS` ходов
(`bot/config.py`, по умолчанию 10) — как при чтении контекста для модели,
так и физически в таблице, чтобы она не росла бесконечно.

Обычное текстовое сообщение и голосовые (распознаются через Groq Whisper)
уходят текстовой модели с доступом к поиску в интернете (DuckDuckGo,
tool-calling — модель сама решает, когда искать свежую информацию). Фото
разбираются в два этапа (сначала точное распознавание, потом решение
премиум-моделью) — можно с подписью-вопросом. PDF-файлы читаются через pypdf
и передаются модели как контекст. Под каждым текстовым ответом — кнопки
«Подробнее» / «Проще» / «Пример» для быстрого уточнения без повторного ввода
вопроса. Есть пакеты безлимита по времени (30 мин / 1 час / 1 день) — не
считают отдельные сообщения, пока активны.

### Групповые чаты

Бот отвечает в группах, только если его упомянуть (`@имя_бота`) или ответить
на его сообщение — иначе он не реагирует на каждое сообщение в чате. Это
работает «из коробки» при стандартной настройке @BotFather — **Group
Privacy** должен оставаться **включённым** (значение по умолчанию): тогда
Telegram сам доставляет боту в группах только упоминания/ответы/команды, а
код бота дополнительно на всякий случай проверяет то же самое. Отключать
privacy mode не нужно — с ним бот получал бы вообще все сообщения в группе.

### Админ-панель

Telegram ID из `ADMIN_IDS` (через запятую) получают доступ к `/admin` —
инлайн-панели со статистикой (пользователи, активность, доход в звёздах за
день/7 дней/всего) и постраничным списком пользователей; по каждому
пользователю — карточка с балансом, последними платежами (с charge_id и
статусом paid/refunded) и кнопками начисления (+10/+50/-10), чатлога и
возврата оплаты, без необходимости печатать ID вручную. Старые текстовые
команды тоже работают:
- `/grant <user_id или @username> <amount>` — начислить/списать сообщения
- `/users` — список пользователей и их лимитов
- `/chatlog <user_id или @username> [N]` — последние N сообщений переписки
- `/refund <telegram_payment_charge_id>` — вернуть оплату через Stars API
  (`bot.refund_star_payment`) и списать выданное обратно (баланс сообщений
  не уходит в минус); работает только для платежей после этой миграции —
  у них есть сохранённый `telegram_payment_charge_id`, у более старых его нет

### Платежи (Telegram Stars)

- Оплата не теряется при передеплое: бот запускается с
  `drop_pending_updates=False`, так что накопившиеся во время рестарта
  апдейты (включая `successful_payment`) не отбрасываются, а обрабатываются
  при следующем старте.
- Начисление идемпотентно: каждый платёж сохраняется с уникальным
  `telegram_payment_charge_id` — если Telegram повторно доставит тот же
  `successful_payment` (например, из-за рестарта в процессе доставки),
  повторного начисления не будет, пользователь получит сообщение «платёж уже
  обработан».
- На pre-checkout бот проверяет, что оплачиваемый пакет реально существует
  в текущих `PACKAGES`/`TIME_PACKAGES`/`SUBSCRIPTION` и цена совпадает —
  иначе отклоняет платёж с понятной причиной, а не берёт деньги за
  несуществующий/устаревший пакет.
- Таблица `payments`: `kind` (`messages`/`unlimited`/`subscription`),
  `amount_stars`, `credited_amount` (сколько сообщений/минут/дней реально
  выдано — не зависит от последующих изменений цен), `telegram_payment_charge_id`,
  `status` (`paid`/`refunded`).

### Монетизация

**Подписка за Stars** (месячная, автопродление): в отличие от разовых
пакетов, создаётся через `bot.create_invoice_link(..., subscription_period=2592000)`
— у `send_invoice`/`answer_invoice` параметра подписки нет вообще, только у
`createInvoiceLink` (Telegram сейчас разрешает только ровно 30 дней).
Ссылка отдаётся пользователю кнопкой `url=...`, а не открывается как обычный
инвойс. Каждое продление приходит отдельным `successful_payment` с новым
`telegram_payment_charge_id`, но тем же `invoice_payload` — идемпотентность
из блока платежей (уникальный индекс по charge_id) сама отличает
редоставленный дубль (не начисляет повторно) от настоящего продления
(стакает ещё 30 дней). Состояние — прямо в `players`:
`subscription_until` (до какой даты активна, стакается как безлимит-пассы),
`subscription_status` (`none`/`active`/`canceled`), `subscription_charge_id`
(последний charge_id — нужен, чтобы вызвать `editUserStarSubscription` для
отмены). Отмена/возобновление — кнопка в «Баланс», которая сначала дёргает
Telegram (`bot.edit_user_star_subscription`) и только при успехе меняет
статус локально; отмена не обрывает доступ сразу, только останавливает
автопродление. `SUBSCRIPTION_PRICE_STARS` — в `config.py` (единственная
цена, вынесенная из `payments.py`, так и было явно запрошено); при смене
всё равно нужно бампнуть `PRICE_VERSION` в `payments.py` в том же деплое.

**Воронка покупок**: таблица `events` (`user_id`, `event`, `created_at`) —
логируются `buy_opened` (открыт экран покупки — и «Баланс», и «Пополнить»),
`invoice_sent` (создан инвойс/ссылка) и `paid` (успешно оплачено, не
дубликат). `/admin` → «📈 Воронка покупок» — конверсия по уникальным
пользователям, отдельно за сегодня и за 7 дней, с процентами между этапами.

**Опциональные напоминания**: кнопка «🔔 Напоминания» в меню — по умолчанию
выключены, включаются и выбираются только самим пользователем (пресеты
09:00–21:00 по `QUOTA_TZ`). Фоновая задача в `main.py`
(`_reminder_loop`, проверка каждые 5 минут) шлёт `players.reminder_hour`
ровно раз в сутки (`reminder_last_sent_date` защищает от повтора) —
никаких рассылок без явного включения, отключить можно в любой момент.

### Реферальная программа

Асимметрично по таймингу — защита от накрутки фейковыми аккаунтами:
- Приглашённый получает `REFERRAL_SIGNUP_BONUS` (по умолчанию 5 сообщений)
  сразу при переходе по ссылке — не гейтится, фейковому аккаунту с парой
  бесплатных сообщений на собственном одноразовом балансе ничего не даёт.
- Пригласившему `REFERRAL_BONUS_MESSAGES` (по умолчанию 20 сообщений)
  начисляется отложенно — только когда приглашённый напишет боту
  `REFERRAL_MIN_MESSAGES` (по умолчанию 3) реальных сообщений (текст, фото
  или PDF — генерация картинок не считается). Плюс дневной лимит
`REFERRAL_DAILY_CAP` (по умолчанию 5) на число *оплаченных* приглашений от
одного пригласившего в сутки — даже если завести сколько угодно фейковых
аккаунтов и разогнать их до порога сообщений, реально обналичить
получится не больше `REFERRAL_DAILY_CAP` в день. Приглашения, упёршиеся в
дневной лимит, не сгорают — остаются `pending` и оплачиваются сами, как
только у пригласившего освобождается место в лимите (на следующий день
или раньше).

Таблица `referrals`: одна строка на приглашённого (`user_id` — PK),
`referrer_id`, `status` (`pending`/`paid`), `message_count`, `paid_at`.
Отдельно от `players.referred_by`, который остаётся как есть (только для
идемпотентности «пригласили один раз, не сам себя»).

### Надёжность

- **Параллельный спам одного пользователя**: per-user `asyncio.Lock`
  (`handlers._get_user_lock`) — пока обрабатывается предыдущее сообщение
  этого пользователя, новое не запускается, в ответ приходит «⏳ Дождись
  ответа на предыдущее сообщение». Не влияет на других пользователей —
  лимит запросов от разных людей друг друга не блокирует.
- **Общий лимит на Groq**: глобальный `asyncio.Semaphore(GROQ_MAX_CONCURRENT)`
  в `bot/ai.py` оборачивает все три места, где код реально стучится в Groq
  (chat completions, STT, перевод промпта для картинки) — не даёт всем
  пользователям вместе выжечь общий rate limit одновременными запросами.
- **SQLite**: при подключении выставляются `PRAGMA journal_mode=WAL`,
  `busy_timeout=5000`, `synchronous=NORMAL` — читатели не блокируют писателя,
  а конкурентная запись ждёт до 5 сек вместо мгновенного "database is locked".
- **Часовой пояс**: дневной лимит сообщений и дневной кап рефералов считают
  сутки по `QUOTA_TZ` (IANA-имя, по умолчанию `Europe/Moscow`) через
  `zoneinfo`, а не по UTC — раньше сброс лимита приходился на 3 часа ночи
  по Москве. Время окончания безлимита показывается пользователю тоже в
  `QUOTA_TZ`, а не в сыром UTC. Все таймстампы в БД по-прежнему хранятся как
  наивные UTC-строки (см. `db._utcnow_naive()`/`db._today_start_utc()`) —
  меняется только то, в каком поясе считаются календарные сутки и что
  показывается пользователю, формат хранения не тронут (иначе сравнения со
  старыми записями сломались бы).
- **Проверка моделей при старте**: `ai.check_configured_models()` запрашивает
  у Groq список доступных моделей и пишет warning в лог для каждой
  настроенной модели (`FAST_MODEL`/`PREMIUM_MODEL`/`VISION_MODEL`/`STT_MODEL`),
  которой там нет — вместо того, чтобы опечатка в id модели вылезала только
  в рантайме на первом же фото/голосовом.
- **Корректное завершение**: при остановке бот закрывает HTTP-сессию
  (`bot.session.close()`) и соединение с БД (`db.close()`, коммитит и
  закрывает) вместо того, чтобы полагаться на обрыв процесса.
- **Ретеншен переписки**: `chat_log` (админский аудит-лог, см. `/chatlog`
  выше — доступ к нему не убран) хранится `CHATLOG_RETENTION_DAYS` дней (по
  умолчанию 30), старые записи удаляются при старте и затем раз в сутки
  фоновой задачей (`main._chatlog_retention_loop`) — иначе таблица растёт
  на диске Railway бесконечно. `dialog_history` в этот ретеншен не входит,
  у неё свой отдельный кап по `MAX_HISTORY_TURNS` (см. выше).

## Локальный запуск

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env  # впиши свои BOT_TOKEN и GROQ_API_KEY
python -m bot.main
```

Ключ Groq берётся на https://console.groq.com/keys (бесплатно, без карты).

## Деплой на Railway

1. Зайди на https://railway.app и залогинься через GitHub.
2. **New Project → Deploy from GitHub repo** → выбери этот репозиторий и ветку.
3. В настройках проекта (Variables) добавь:
   - `BOT_TOKEN` — токен бота от @BotFather
   - `GROQ_API_KEY` — ключ от console.groq.com
4. Railway автоматически соберёт проект (Nixpacks) и запустит команду из
   `railway.json` / `Procfile` (`python -m bot.main`).

Баланс/лимиты/заметки хранятся в SQLite-файле. На бесплатном плане Railway
диск по умолчанию эфемерный и сбрасывается при каждом деплое — обязательно
подключи Railway Volume (`railway volume add --mount-path /data`) и укажи
путь через него в переменной `DB_PATH` (например `/data/assistant.db`),
иначе все балансы и покупки будут пропадать при каждом обновлении кода.
